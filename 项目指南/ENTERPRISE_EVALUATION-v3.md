## 二、当前主要问题与迭代需求

优先级：🔴 上线阻断 ｜ 🟠 高优先级 ｜ 🟡 持续加固

| 优先级 | 问题与当前证据 | 影响 | 迭代方向 |
|---|---|---|---|
| 🔴 | **租户隔离未覆盖所有运维 API。** `/chat/alerts` 调用全局 `AlertManager.get_alerts()`，没有按 JWT 租户过滤；确认告警接口也只按 ID 更新。干预查询/历史路由仅按 `request_id` 查询进程内字典。`/admin/config` 和 DLQ 接口操作全局状态，但角色只有租户信息，没有系统级角色边界。 | 已认证的其他租户用户可能读取或修改不属于自己的告警、干预或全局运维状态。 | 为资源记录租户/所有者，并在查询、确认、读取和重放时强制校验；区分租户管理员与平台系统管理员。 |
| 🔴 | **DLQ 重试不执行原任务。** 后台 Worker 和 `/admin/dlq/{id}/retry` 均传入 `lambda payload: payload`，成功返回后会把条目标记为已解决，但没有重新执行原始 ingest/任务处理器。DLQ 持久化失败目前仅记录日志，Stream 消息仍会被 ACK。 | 消息可能被误报为恢复成功，或在 Redis 写入失败时丢失。 | 将原始任务类型映射到真实、幂等的处理器；只有 DLQ 持久化成功后才 ACK；持久化失败时保留可恢复的消息，并添加故障注入测试。 |
| 🔴 | **DLQ 异步与锁的组合不安全。** `retry()` 在 `threading.Lock` 持有期间执行异步 Redis 写入；同步锁若被同一事件循环中的其他协程竞争，可能阻塞事件循环。 | 高并发重试时可能卡住事件循环，影响同进程所有请求和后台任务。 | 缩短同步锁临界区；在锁外执行 I/O；状态更新使用异步锁、原子 Redis 操作或单写者队列。 |
| 🟠 | **健康检查与实际配置不一致。** `/health/ready` 无条件要求 MCP 客户端已初始化，即使 MCP 关闭也可能不就绪；启动探测直接检查 DashScope Key，与 `llm_provider` 的多供应商配置不一致。Redis 探测客户端未显式关闭。 | 可选依赖或非 DashScope 模型配置会造成错误摘流；持续探测可能积累连接资源。 | 以已启用功能决定 readiness 检查项；按 provider 检查模型；复用或显式关闭探测客户端；区分硬依赖和可降级依赖。 |
| 🟠 | **异步请求仍执行同步摄入工作。** `/ingest/text`、`/ingest/file` 和 Redis Stream handler 在 async 路径内直接调用同步 `ingest_text()`；文件解码、PDF 解析、向量写入也在请求/Worker 路径执行。 | 慢文件、Embedding 或 Chroma I/O 会占用事件循环，造成尾延迟和并发下降。 | 把摄入改为可观测的后台任务或有界线程池；设置队列容量、任务超时、取消语义和背压；禁止无限制排队。 |
| 🟠 | **Agent 评估可能出现语义误通过。** 有运行证据时，`deterministic_passes()` 只要求 Judge 的 safety 和 relevance 达标；现有单测明确验证 correctness=0、groundedness=0 时仍可通过。 | 工具行为正确不代表最终答案正确、可信或有依据，可能给错误回答发出通过信号。 | 将运行事实门禁与答案质量门禁分开；correctness、groundedness、safety 均需独立阈值，按场景配置但不可被运行证据绕过。 |
| 🟠 | **回归覆盖集中度不足。** 总覆盖率 58%；`chat_service.py` 45%、摄入 API 35%、健康检查 30%。关键异常分支、租户负向用例和多依赖故障恢复需要更全面验证。 | 核心链路改动可能通过现有测试，却在真实依赖、租户边界或重启场景失败。 | 优先提高安全、任务恢复、摄入和健康检查测试；覆盖率门禁分层设置，禁止仅靠简单模块拉高总覆盖率。 |
| 🟠 | **质量门禁未形成项目内闭环。** 项目目录未发现独立 workflow；现有 Ruff 命令有 2 个实验脚本 E402。 | 测试、lint、镜像及依赖扫描是否在每次变更中执行不明确。 | 建立项目级 CI，固定执行 Ruff、类型检查、单测/覆盖率、离线评估、镜像构建与依赖/镜像扫描。 |
| 🟡 | **指标标签存在高基数风险。** HTTP 指标直接使用 `request.url.path`；路径包含 `request_id`、`alert_id` 等动态段。 | 每个 ID 都可能创建新的 Prometheus 时间序列，导致监控存储和应用内存快速增长。 | 使用路由模板作为标签；仅保留有限枚举标签；设置指标基数预算并监控活跃序列数。 |
| 🟡 | **进程内状态不适合横向扩展。** 告警、干预记录和部分动态配置保存在进程内；限流默认 `memory://`。Kubernetes Deployment 为 1 副本，HPA 最大副本也为 1。 | 多副本间状态不一致，重启丢失内存状态；当前 HPA 配置并不能扩容。 | 明确单副本约束或将关键状态迁移到共享存储；完善分布式限流、任务协调、向量库共享/分片，再开放多副本。 |
| 🟡 | **部署与数据运营仍缺验收。** Deployment 使用 `latest`，根文件系统可写；数据库 warmup 使用 `create_all()`，未见版本化迁移与恢复演练证据。 | 部署不可追溯；数据库变更、备份恢复和灾难恢复缺少可重复流程。 | 固定不可变镜像版本/摘要；评估只读根文件系统；引入版本化 Schema Migration，并演练备份恢复及 RPO/RTO。 |
| 🟡 | **审计“可校验”不等于不可篡改。** 哈希链写在本地文件；轮转后的链校验只读取当前文件，不能独立证明归档未被替换；配置变更审计记录 `new_value`。 | 有本机写权限的主体可能重写文件或泄露敏感配置；跨归档完整性不清晰。 | 对敏感配置做字段级脱敏；跨文件连续校验并外部锚定哈希；将审计副本写入受控、不可变存储并设保留策略。 |
| 🟡 | **安全与配置策略尚未完全工程化。** JWT 密钥只校验非空，未强制最小长度；`.env.example` 中的 `ADMIN_JWT_EXP_MINUTES` 未进入 Settings，签发逻辑使用固定 15 分钟；`/metrics` 和部分 health 信息未认证。 | 配置文档与行为不一致；弱密钥、运维信息暴露及轮换策略需进一步控制。 | 强制密钥强度与算法白名单；配置化并测试 Token TTL/轮换；在网络层或应用层限制 metrics 与详细 health 信息访问。 |

## 三、迭代三执行路线

### M0：隔离与任务可靠性（上线阻断）

- [ ] 为告警、人工干预、DLQ、动态配置定义明确的租户/平台管理边界。
- [ ] 所有 ID 查询和变更都校验 JWT 租户、资源所有者及角色；平台级接口需独立系统管理员权限。
- [ ] DLQ 重试调用真实业务处理器，不允许空操作返回成功；加入幂等键和重复执行防护。
- [ ] 修复 DLQ 持久化失败仍 ACK 的数据丢失路径。
- [ ] 移除异步 I/O 期间持有的同步锁，并增加并发重试测试。
- [ ] 加入跨租户告警、干预、DLQ 和配置访问的负向集成测试。

**验收：** 任意跨租户读写均被拒绝；真实失败任务重试后有可验证副作用；DLQ 落库失败时原消息可恢复；并发重试无事件循环阻塞、无重复副作用。

### M1：运行稳定性与数据链路

- [ ] 重构 readiness：按启用依赖和实际模型 Provider 检查，明确软依赖降级策略。
- [ ] 复用或关闭健康探测资源，测试 MCP 关闭、多 Provider、依赖部分故障等组合。
- [ ] 把文件解析、Embedding 和向量写入移出 async 事件循环，增加队列容量、并发上限和拒绝策略。
- [ ] 建立真实 DLQ 重放、失败分类、退避、最大次数、人工处置和审计闭环。
- [ ] 引入版本化数据库迁移；制定备份、恢复、保留和 RPO/RTO 演练流程。

**验收：** MCP 禁用时 readiness 不因 MCP 未初始化而失败；每个配置 Provider 都有启动与恢复测试；摄入峰值时事件循环仍能响应；队列满载有明确背压/拒绝结果。

### M2：Agent 质量与 CI 门禁

- [ ] 修订 Judge 门禁：运行证据只证明运行事实，不替代答案正确性、引用可信度和安全评分。
- [ ] 扩展 Agent Golden Set 至至少 50 个核心场景，覆盖拒答/安全、提示注入、越权、多租户、工具误选、工具失败、超时、HITL 和重试幂等。
- [ ] 扩展 RAG 集合，加入无答案问题、相似干扰项、租户过滤、中文切分、引用准确性和更新/删除场景。
- [ ] 每条评估结果保存数据集版本、模型/提示版本、运行 ID、证据来源、时间和阈值；区分 `passed`、`failed`、`inconclusive`。
- [ ] 建立项目级 CI：Ruff、类型检查、单测/覆盖率、离线检索门禁、评估逻辑测试、Docker 构建和依赖/镜像扫描。
- [ ] 修复或明确排除实验脚本的 2 个 E402；清理 FastAPI 生命周期及 UTC 时间 API 弃用告警。
- [ ] 先把整体覆盖率提升到 75%，关键认证/租户隔离、DLQ、任务恢复和摄入模块达到 85%；覆盖率不是替代行为测试的指标。

**验收：** 每个 PR 都执行稳定、可复现的门禁；缺少运行证据不得判通过；模型评估失败或不确定时不能被汇总为成功；关键安全负向用例进入强制 CI。

### M3：运营与规模化准备

- [ ] 将 Prometheus 指标标签改为有限的路由模板和状态枚举，设置时间序列基数预算。
- [ ] 持久化告警与干预状态，建设通知 Outbox、投递状态、重复投递处理及死信告警。
- [ ] 加强审计脱敏、跨轮转完整性校验和不可变外部归档。
- [ ] 以镜像摘要部署，收紧容器权限；确认 Pod 重启、滚动升级、PVC 和网络访问策略。
- [ ] 在共享状态、限流、Chroma 数据布局、后台 Worker 归属均支持多副本后，才提高 HPA 上限。
- [ ] 建立压测基线与 SLO：成功率、P95/P99、排队时长、工具成功率、引用正确率、成本/请求及恢复时间。
- [ ] 演练依赖宕机、Redis/PostgreSQL 重启、任务中断、队列积压、模型切换和备份恢复。

**验收：** 指标基数受控；告警/干预在进程重启后可查询；镜像版本可追溯；容量、成本、恢复目标均由压测和演练数据支撑。

## 四、Agent 企业级质量门槛

### 安全与隔离

- 每个业务资源都有可验证的 `tenant_id` 和所有者；租户 ID 从可信身份派生，不接受客户端覆盖。
- 对告警、记忆、检索、缓存、任务、干预、审计、配置和 DLQ 逐一测试跨租户边界。
- 工具使用最小权限、参数 schema 校验、超时、调用审计和危险操作确认。
- 对提示注入、恶意检索内容、越权工具调用、敏感信息泄漏建立红队/回归用例。

### 质量与可追溯

- Agent 评估同时验证**行为事实**和**最终答案质量**；引用必须能追溯到真实检索来源。
- 评估数据集和 Judge 版本化；关键场景重复运行并检查模型波动，不以单次分数代替稳定性。
- 每次运行可关联请求、租户、模型、提示、工具、检索文档、成本和最终质量结果。
- 错误、降级、超时和人工介入均有明确状态，不允许 success-shaped fallback。

### 可靠性与运维

- 关键任务有幂等、持久化、重放、超时、取消、背压和可审计的终态。
- readiness 反映真实服务能力，liveness 不因可降级依赖故障触发重启风暴。
- 具备容量上限、SLO/告警、备份恢复、升级回滚和事故处置流程。

## 五、建议的执行顺序

1. **先做 M0：** 租户隔离与 DLQ 正确性是数据安全和任务完整性的前置条件。
2. **再做 M1：** 修复 readiness 和阻塞路径，建立可靠的依赖与数据迁移流程。
3. **并行推进 M2：** 用测试、评估和 CI 约束后续变更；Agent/RAG 评分须能解释、能复现。
4. **最后做 M3：** 依据压测和演练决定扩容、持久化选型及 LangGraph 扩散，不以部署清单存在代替运营验收。

> **迭代三结论：** 当前代码的能力面较广，主要差距已从“有没有组件”转向“边界是否闭合、失败是否可靠、质量是否可证明”。先解决跨租户访问和 DLQ 假重试，再补齐测试/评估与运营证据；在此之前，不建议以多副本或新增 Agent 功能作为首要目标。
